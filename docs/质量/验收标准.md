# Agent CIL V2 验收标准

## 1. 架构边界

| 项目 | 验收要求 |
| --- | --- |
| Core 依赖 | 不直接依赖 CLI、具体模型 SDK、Shell 实现或 UI |
| Session 状态 | 只有 Event Journal 是权威事实来源 |
| 生命周期 | Thread / Turn / Step 状态转换有契约和测试 |
| Agent Loop | 只负责模型、工具和终止条件的编排 |
| 扩展边界 | 插件不能覆盖状态机、事件提交语义或 Execution Guard |

## 2. 多模型能力

- 至少支持 Anthropic Messages、OpenAI Responses、OpenAI-compatible Chat 三类协议。
- 每类 Provider 通过同一套内部请求与响应契约测试。
- 流式文本、工具调用、usage、stop reason 和错误分类正确。
- Provider-private reasoning / signature / cache state 不被错误转换或静默丢弃。
- 真实 Provider 验收与本地 Fixture 验收分别报告。

## 3. 工具执行一致性

- toolCallId 在整个执行生命周期内稳定。
- 每个 tool_call 都有匹配的结果或明确终态。
- Schema 校验先于授权和执行。
- `updatedInput` 发生变化时重新校验、重新授权。
- `deny` 为终态；缺少审批处理器时 fail closed。
- 只读并发与写操作互斥策略明确。
- 工具结果回填顺序确定且可恢复。

## 4. 安全

- 所有原生、MCP 和扩展工具通过统一 Execution Guard。
- Sandbox 实际限制文件、进程、网络和环境变量权限。
- 工作区路径校验不能只依赖字符串前缀。
- 未授权操作不能产生受保护副作用。
- 审批绑定精确输入、调用 ID 和资源范围。
- 取消、拒绝和崩溃不能导致授权绕过。
- 日志和工具输出不泄漏凭证或敏感上下文。

## 5. 崩溃恢复

必须通过故障注入覆盖：

- 事件追加前后崩溃；
- 模型响应开始前、流式过程中和提交后崩溃；
- 工具意图写入后、进程启动前崩溃；
- 工具进程执行中崩溃；
- 副作用完成但结果事件尚未提交时崩溃；
- 审批等待期间崩溃；
- Compaction 生成摘要期间崩溃。

恢复必须能区分已完成、未执行、可安全重试和 `outcome_unknown`。任何未知副作用不得自动盲目重放。

## 6. 上下文与长任务

- Compaction 不拆散 Assistant tool_call 与 tool_result。
- 最近必要的工具历史和 Provider 原生状态按规则保留。
- 摘要生成失败不修改原上下文。
- 事件历史始终完整。
- Fork 后授权和执行进程不继承。
- 长会话恢复后能够继续完成原任务。

## 7. Coding 能力 Benchmark

至少覆盖：

- 跨多个文件实现功能；
- 修复失败测试；
- 仓库内搜索与定位；
- Read → Edit → Test → Fix → Retest；
- 长会话多轮连续开发；
- Provider 断流和恢复；
- 工具执行崩溃和不确定结果处理。

比较时固定模型版本、任务、工具集、权限、预算、上下文和运行环境。报告成功率、成本、延迟、错误分类和恢复正确性。

## 8. 发布门槛

- 所有核心契约测试通过。
- Sandbox 与权限测试通过。
- 故障注入恢复测试通过。
- 三类 Provider 契约测试通过。
- 真实 Coding 任务成功率不低于既有基线。
- 依赖、许可证、凭证、日志和发布产物审计完成。
